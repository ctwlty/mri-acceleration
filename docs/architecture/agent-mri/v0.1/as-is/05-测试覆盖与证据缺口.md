# 05｜测试覆盖与证据缺口

## 1. 本页如何解释“覆盖”

- **测试源码覆盖**：当前 HEAD 存在对应断言和 CMake 注册。
- **历史运行证据**：已有日志记录某次通过，但必须标明它绑定的提交/构建。
- **当前 HEAD 已验证**：必须由 `91343be...` 的新鲜 configure/build/test 证据支持。

本次任务严禁启动程序/SDK/设备，并以只读审计为主；没有重新构建或执行 CTest。因此下表的“已覆盖”
均表示测试源码存在，不表示本轮运行通过。

## 3. Mock 主链源码覆盖

### 状态模型

`test_mock_workflow.cpp` 覆盖：

- HistoricalRaw/LiveBlocked 不生成 run identity；
- 准备证据缺失不生成 identity；
- 合法 Mock start 接受非空 run/snapshot ID 并冻结；测试用注入式生成器证明两次测试结果不同，但不证明生产跨历史唯一性；
- pause/resume/cancel 保留身份、清结果；
- Processing→Reconstruction→QC→Packaged；
- 失败及 QC hash 不匹配清图/QC。

### 结果包/历史

`test_mock_result_package.cpp` 覆盖：

- 6 工件 + manifest 共 7 文件；

## 4. 测试本身的已验证缺口

### 4.1 提前返回的“全控件”测试

`visibleWorkflowControlsHaveNamesAndObservableBehavior()` 在
`client/tests/test_main_window.cpp:672` 无条件 `return`；`:674-852` 的交互断言不执行。

因此，函数名不能作为“所有可见 enabled 控件都有反馈”的证明。这也解释了为何按钮问题可能在其他局部测试通过时仍存在。

### 4.2 被禁用的 automation GUI 测试

`client/tests/test_main_window.cpp:207-378` 整段在 `#if 0` 内，包括：

- automation 显示两张图且不 Run；
- 运行时锁控制模式；

- 外部进程运行中阻止关窗。

当前 CTest 中的 `gui_automation_mode_fake` 只证明 GUI 配置后保持 idle；不能替代这些已禁用测试。

### 4.3 测试固化了部分断路行为

- `test_main_window.cpp:854-880` 把“第 12 页从左栏重新选模板后跳到 03”当作期望。
- `:2137-2182` 明确点击页内 Save，再点 History；没有要求第 12 页全局 Next 代理 Save。
- QA 测试允许 Empty workflow 打开深页，这是设计的测试入口，不是生产页面合法性证明。

## 6. 关键未覆盖风险

### 产品/导航

- 页面状态与 `MockWorkflowState` 的全组合不变量；
- 第 02 页中栏模板 radio 与左栏 catalog 选择分裂；
- Processing→08、QcReady→07 后旧 run 的明确归宿与审计；
- Packaged 后显式结束/新任务语义；
- 重启后已有磁盘历史的正常入口；
- 下一任务清空或继承 FSE B、L2、定位几何和成像目标。

### 异步/错误/恢复

- Running/Paused 时关闭窗口；
- 取消确认、应用崩溃、重启恢复；
- QC/写包/history 的进度、超时、取消和 UI 响应；
- Failed 的阶段类型与合法 retry 目标。

### 数据/事务

- 磁盘满、权限中途变化、单文件写一半、staging 清理失败、rename 失败；
- 多进程并发写相同结果根；
- writer 成功而 `markPackaged()` 失败；
- 内存/磁盘 `PACKAGE_SAVED` 一致性；
- Cancelled/Failed 审计跨进程持久化；
- 大历史根的内存/延迟上限；
- history source 按钮实际解析来源，而非只显示路径。

### 身份/安全

- `softwareCommit == 当前 HEAD`、dirty tree、资源 hash、构建配置；
- manifest 自身可信锚/签名和额外未声明文件；
- 默认发行包不含或不可触发真实 SDK/代理能力；
- `--mock-step + --auto-connect` 模式隔离；
- 当前 HEAD 无参数完整 Mock 链中 LoadLibrary/SDK/eggcontroller 调用严格为 0。

### 真实设备（本产品边界下应保持 BLOCKED）

- DLL/设备身份、IDLE、协议/横断位映射、真实 snapshot、隔离输出、唯一 owner、单次授权；
- 真 SDK 函数卡死时的 watchdog；
- RAW 与 run/snapshot/hash 的强绑定。
