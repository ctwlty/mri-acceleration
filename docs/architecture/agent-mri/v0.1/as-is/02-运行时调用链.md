# 02｜运行时调用链

## 1. 入口分流

### 1.1 默认无参数 GUI

```text
main.cpp::main
  → QApplication / app.qss
  → MainWindow::MainWindow
      → new EggControllerProcess
      → new DeviceBridge（其内部持有 MriSdkLoader，但此时不 load）
      → buildLeftPane + buildCenterPane + buildRightPane
      → 创建两个 13 页 QStackedWidget
      → 创建单次 Mock QTimer
  → MainWindow::show
  → QApplication::exec
```

- **VERIFIED FACT**：默认路径不调用 `loadSdkAndConnect`，证据为 `client/src/main.cpp:111-136`。
- **VERIFIED FACT**：真实按钮在构造和每次状态刷新时都保持禁用，证据为
  `MainWindow.cpp:1069-1126,5605-5638`。
- **INFERENCE（高置信）**：在没有 CLI 注入、测试直接调用或未来重新接线的前提下，默认可见 Mock 流程静态不可达 SDK/Run/Abort。

### 1.2 QA 跳页

`--mock-step N` → `MainWindow::setMockWorkflowStep(N)`（`main.cpp:77-85`）→
重建一个 Empty `MockWorkflow`、清三个确认，然后直接设置页面（`MainWindow.cpp:4356-4363`）。

这条路径用于页面取证，不代表已完成前置步骤。10–13 页在该模式下应显示 Empty/禁用状态。

### 1.3 显式真实 auto-connect

```text
--auto-connect --sdk/--init/--par/--output
  → QTimer::singleShot(0)
  → MainWindow::loadSdkAndConnect
  → DeviceBridge::loadSdk
  → MriSdkLoader::load → LoadLibraryW + GetProcAddress
  → DeviceBridge::connectDevice
  → MriSdkLoader::initialize → Init/ConfigFile/SetOutputPath/...校准
  → DeviceBridge state=Ready
```

证据：`main.cpp:27-41,113-135`、`MainWindow.cpp:5400-5410`、
`DeviceBridge.cpp:32-95`、`MriSdkLoader.cpp:22-51,125-218,429-469`。

- **VERIFIED FACT**：它可以与 `--mock-step` 同时传入；参数校验只禁止 automation 与 auto-connect 组合（`main.cpp:63-85`）。
- **VERIFIED FACT**：建链后可见真实 Run/Abort 仍禁用，UI 和底层状态可能出现“Mock 文案 + Ready 会话”的双轨。
- 本次审计没有执行该链。

### 1.4 eggcontroller automation 参数

```text
--automation-python/--automation-root/--automation-proxy
  → main 校验路径
  → MainWindow::configureEggController
  → 仅保存 EggControllerLaunchConfig + 显示“保持 HOLD”
  → 无 EggControllerProcess::start 调用
```

证据：`main.cpp:46-74,86-109`、`MainWindow.cpp:914-920`；生产 `client/src` 中不存在
`m_eggController->start(...)` 调用。

- **VERIFIED FACT**：`EggControllerProcess` 和 Python proxy 都存在，但当前生产 GUI 没有启动边。
- **VERIFIED FACT**：若未来直接启动 proxy，它会把旧程序 demo 设为 false 并调用
  `samplingBtn_click_sync()`（`client/tools/eggcontroller_proxy.py:46-64`）。
- **INFERENCE（高置信）**：基于该调用行为，不能把这个 proxy 归类为无真实副作用的 Mock 接口。

### 1.5 独立 `mri_sdk_verify`

该工具不是 GUI 页面路径：

```text
mri_sdk_verify --sdk --init --par --output [--scan]

  → 若有 --scan：DeviceBridge::startScan
```

证据：`client/tools/mri_sdk_verify.cpp:22-145`。部署脚本会把该工具和 Mock GUI 一起复制到 dist
（`client/scripts/deploy.ps1:24-44`）。本次审计没有执行它。

## 3. Mock 状态调用顺序

```text
Empty
  → prepare(draft, evidence) → Prepared
  → start(confirmations)     → Running + runId + snapshotId
  → pause/resume             ↔ Paused
  → setProgress(100)         → Processing
  → bindReconstruction       → Reconstructed
  → recordQcSuccess          → QcReady
  → confirmResult            → QcReady(resultConfirmed=true)
  → MockResultPackage::write → 磁盘包
  → markPackaged             → Packaged
```

错误/取消分支：

- Running/Paused → `cancel()` → Cancelled；保留 run/snapshot/audit，清结果，UI 回 08。
- Running/Paused/Processing/Reconstructed/QcReady → `fail()` → Failed；清结果。
- 任意拥有 run/snapshot 的 Failed → `retryProcessing()` → Processing；当前模型不记录失败阶段，
  因而 Running 阶段失败也可能跳到 Processing。
- Cancelled/Packaged 没有领域内恢复；新运行由 `MainWindow::startMockRun()` 创建全新 candidate 覆盖旧对象。

证据：`client/src/app/MockWorkflow.cpp:303-529`。

## 4. 页面跳跃为何发生

### 4.1 页面与领域状态没有强绑定

`setWorkflowStep()` 只限制 1..13，并同步两个 stack；它不校验目标页是否与
`MockWorkflowState` 相容（`MainWindow.cpp:4273-4354`）。因此：

- QA API 可把 Empty 模型放到任意页；
- 10→8、11→7 只换页面，不把旧 Processing/QcReady run 明确转成 Cancelled/Failed；
- 下一次 `startMockRun()` 会用全新 candidate 覆盖旧模型，旧 run 无“放弃/另存草稿”审计。

### 4.2 场景/模板选择也承担路由

- 左栏“使用所选模板”可从任意非运行页 `applyScene()` 清模型并跳 03
  （`MainWindow.cpp:1134-1141,5717-5723`）。
- 选择非 catalog index 0 的模板且当前页 >02 时，`handleSceneChanged()` 强制跳回 02
  （`:5383-5397`）。
- 场景、对象、搜索变化都可能进入该 handler（`:5365-5381`）。

### 4.3 为什么可能出现“中栏参考模板已选，但下一步禁用”

正常从 01 进入 02 时，`setWorkflowStep()` 会在一级场景尚未选择时自动选第一项；随后 signal 链填充对象、
模板并选中 catalog index 0（`MainWindow.cpp:4286-4288,5294-5357`）。因此这不是默认首次进入必现的断点。

但源码确实维护两套选择状态，用户切换到非基线场景/模板或搜索结果后可能出现分裂：

1. 构造器最终把左栏两个 combo 设为 `-1`，清空 `sceneList`，放入不可选占位项
   （`MainWindow.cpp:296-316`）；进入 02 时再由上述自动选择链重建左栏状态。
2. 第 02 页的“水模横断位成像模板”radio 默认选中，只控制卡片样式/对照标志
   （`:1428-1501`）。
3. 第 02 页 CTA 和全局 Next 的 enabled 却取决于**另一个控件**：左栏 `sceneList` 当前项的
   `Qt::UserRole == 0`（`:1512-1518,4460-4478`）。
4. 所以当左栏当前项不是 index 0 时，中栏仍可能显示默认选中的参考模板 radio，而 Next 保持禁用。

“两套状态源未合并”是 VERIFIED FACT；它是否就是某次现场截图的唯一根因，在没有该次事件序列证据时保持 unknown。

## 5. 按钮为何重复

部分核心动作存在三层代理入口：

1. 页内 canonical CTA，例如 `MockAcquireButton`；
2. 底部 `WorkflowNextButton` 按 objectName 找到 canonical 后调用 `click()`
   （`MainWindow.cpp:1245-1267`）；
3. 左栏 `LeftMockStartButton` 再代理 `MockAcquireButton->click()`（`:1147-1152`）。

canonical action 映射还复制在：

- `buildCenterPane()`：`:1246-1259`，负责点击代理；
- `refreshWorkflow()`：`:4417-4429`，负责一般页面 enabled/text；
- `refreshMockWorkflowUi()`：`:4255-4269`，负责 10–12 页覆盖。

另一些外观重复不是点击代理：`UseSelectedTemplateButton` 与 `ShowRecommendedTemplateButton` 有各自 handler，
页内 Back 与全局 Back 也分别实现路由。除此之外，`makeLegacyWorkflowPage()` 和 `buildLegacyRightPane()` 保留整套旧页面/状态视图但无调用点
（`:3018-3224,4795-4838`）。

- **VERIFIED FACT**：全局 Next 与左栏 Mock Start 是点击代理；模板/Back 等重复入口则是独立 handler。
- **INFERENCE（高置信）**：映射复制和 objectName 查找让任何漏掉 `refreshWorkflow()` 的路径都可能造成
  “页内按钮有反应、全局按钮无反应”或相反。

## 6. 第 12 页为何偏离统一 Next 链

**VERIFIED FACT**：第 12 页是两阶段动作，但全局导航只表达第二阶段：

1. 到达 12 且结果已确认时，`SaveResultPackageButton` 被启用；
2. `OpenHistoryButton` 只有模型进入 Packaged 后才启用（`MainWindow.cpp:4104-4128`）；
3. 第 12 页全局 Next 映射的却是 `OpenHistoryButton`，不是 Save
   （`:1255-1259,4425-4430,4252-4269`）；
4. 因此用户必须先发现并点击页内 Save，统一 Next 才恢复；纵向测试也是手动点 Save 再点 History
   （`client/tests/test_main_window.cpp:2137-2182`）。

**INFERENCE（高置信）**：若产品期望统一 Next 形成连续闭环，这构成 UX 断点；若产品有意要求用户先在页内
显式封存、再进入历史，则它是两阶段设计而非必然缺陷。源码本身不能决定该产品语义。

封存后仍没有显式“完成任务/新建任务”：

- Packaged 是领域终态；
- 12/13 只在结果与历史之间返回；
- 可通过左栏模板按钮隐式 `applyScene()` 清状态并跳 03，也可改变左栏场景/搜索触发
  `handleSceneChanged()` 跳回 02；两者都不是显式“新建任务”命令（`:5365-5397,5717-5723`）。

另外，历史入口依赖**当前内存模型已 Packaged**，而不是结果根是否已有 manifest。因此应用重启后，
磁盘虽可能有历史，正常 UI 仍没有直接开放历史的路径。这是高置信推断，尚未做运行验证。
